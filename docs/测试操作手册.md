> 适用阶段：T1–T9 已完成（T10 收尾进行中）。

> 自动化 API 回归见 `docs/联调测试报告.md` 与 `ruoyi-takeout-shop/scripts/integration-test.sh`（本文档是其人工补充：覆盖界面与交互）。

## 一、环境准备

### 1.1 必要软件

| 软件 | 用途 | 检查命令 |
|---|---|---|
| Docker Desktop | 跑 MySQL/Redis/RocketMQ | `docker --version` |
| JDK 17+（本机 21） | 跑后端 | `java -version` |
| Node.js 18+ | 跑管理端前端 | `node -v` |
| HBuilderX + 微信开发者工具 | 跑小程序 | — |

### 1.2 ⚠️ 启动前必做：腾出 3306/6379 端口

本机装了 **phpstudy 自带的 MySQL/Redis 且开机自启**，会抢占 3306 导致容器起不来（已多次实际发生）。

**做法**：打开 phpstudy 面板 → 停止 MySQL 与 Redis → 并在「设置/开机自启」中关闭它们的自启动。

验证端口已让出（无输出即为已让出）：

```bash
netstat -ano | grep -E ":3306|:6379" | grep LISTENING
```

### 1.3 一键启动依赖环境（第 1 个终端）

```bash
cd C:\software\code\takeout\ruoyi-takeout-shop
docker compose up -d
docker compose ps
```

期望：4 个容器 `takeout-mysql`、`takeout-redis`、`takeout-rocketmq-namesrv`、`takeout-rocketmq-broker` 均为 **Up**，其中 mysql/redis 显示 **(healthy)**。

> 首次启动会拉镜像（走国内加速源）并自动建库建表，约 1–3 分钟。
> 端口映射：MySQL 3306、Redis 6379、RocketMQ NameServer 9876、Broker 20911、控制台（可选）8180。

**验证数据库已初始化**（应输出 13 张 biz 表 + 店铺名）：

```bash
docker exec takeout-mysql mysql -uroot -proot --default-character-set=utf8mb4 -N -e "select count(*) from information_schema.tables where table_schema='takeout' and table_name like 'biz_%'; select shop_name from takeout.biz_shop_info;"
```

### 1.4 启动后端（第 2 个终端）

```bash
cd C:\software\code\takeout\ruoyi-takeout-shop
java -jar ruoyi-admin/target/ruoyi-admin.jar --takeout.wx.mock-enabled=true
```

- **必须带 `--takeout.wx.mock-enabled=true`**：没配置真实微信 appid 时，这是小程序能登录的唯一方式（开发辅助开关，正式上线须关闭）。
- 若 `ruoyi-admin.jar` 不存在，先编译：`mvn clean package -DskipTests`（需 Maven；本机 Maven 路径见「八、常见问题」）。
- 期望看到 `若依启动成功` 与 `(♥◠‿◠)ﾉﾞ`，日志中应含 `[敏感词] 词库加载完成：24 个词条`。
- **此窗口保持打开**；服务地址 `http://localhost:4121`。

### 1.5 启动管理端前端（第 3 个终端）

```bash
cd C:\software\code\takeout\ruoyi-takeout-shop-web
npm run dev
```

浏览器打开 **http://localhost**（dev 端口为 80），用 **admin / admin123** + 验证码登录，左侧应出现「外卖管理」菜单（店铺信息 / 分类管理 / 菜品管理 / 订单管理 / 退款管理 / 留言管理）。

### 1.6 启动小程序（HBuilderX）

1. HBuilderX → 文件 → 导入 → 本地目录 → 选 `C:\software\code\takeout\takeout-uniapp`；
2. 微信开发者工具 → 设置 → 安全设置 → **开启服务端口**；
3. HBuilderX → 运行 → 运行到小程序模拟器 → 微信开发者工具；
4. appid 留空会用测试号；`manifest.json` 已配 `urlCheck:false`（不校验合法域名）。

> 浏览器（H5）也能调试：HBuilderX → 运行到浏览器。H5 环境走的是「本地调试标识登录」（`utils/request.js` 条件编译），与开发者工具的用户是**两个不同账号**，购物车/地址不互通，属正常现象。

## 三、管理端测试（浏览器，admin/admin123）

### T2-1 店铺信息（含配送费/起送价/营业状态）

1. 「外卖管理 → 店铺信息」→ 检查各字段与上表一致；
2. 把**外卖配送费改成 8.00、起送价改成 30.00** → 保存 → 提示「保存成功」；
3. **验证缓存已删**（Cache-Aside 只删不更新）：
   ```bash
   docker exec takeout-redis redis-cli exists takeout:shop:1
   ```
   期望输出 `0`（表示已删除，下次请求会回填新值）。

### T2-2 分类管理

1. 新增分类「测试分类」→ 列表出现；
2. 再新增同名「测试分类」→ 应被拒绝（提示「分类名称【测试分类】已存在」）；
3. 删除「测试分类」→ 成功；
4. **不存在的拦截**：尝试删除「阿婆招牌」（下面有菜品）→ 应提示「分类【阿婆招牌】下存在菜品，不允许删除」。

### T2-3 菜品管理（CRUD + 图片 + 售罄 + 上下架 + 缓存）

1. 「新增」→ 填名称「测试菜」、所属分类「清爽小食」、售价 12、**上传一张图片**（jpg/png/webp，≤5MB）→ 确定 → 列表出现且缩略图正常；
2. **验证图片只存相对路径**（不应含 http 域名）：
   ```bash
   docker exec takeout-mysql mysql -uroot -proot --default-character-set=utf8mb4 -N -e "select name,image from takeout.biz_goods where name='测试菜';"
   ```
   期望形如 `测试菜 | /profile/upload/2026/09/26/xxxx.png`；
3. **上传校验**：再试上传 6MB 图片 → 应提示「上传文件大小不能超过 5MB」；上传 .gif → 应提示后缀不允许；
4. **规格与口味**：修改「测试菜」→ 加两条规格（如「加量 +2」「少量 −1」）与一组口味（如「甜度：少糖,多糖」）→ 保存 → 再打开确认已保存（验证先删后插的级联）；
5. **售罄开关**：把「测试菜」行内售罄开关打开 → 提示已标记；再关闭；
6. **上下架**：把「测试菜」下架 → 提示成功；
7. **批量售罄**：勾选「测试菜」→ 点「标记售罄」→ 成功；再点「取消售罄」；
8. **缓存**：任一次写操作后执行 `docker exec takeout-redis redis-cli exists takeout:goods:list`，期望 `0`；
9. **清理**：删除「测试菜」（勾选 → 删除）。

### T6/T7 订单与退款管理（需先在小程序下单，见第四节；此处先了解入口）

- 「订单管理」：按状态筛选、操作列按钮随状态变化（接单/出餐/开始配送/确认送达/确认完成）、详情弹窗看明细与规格口味与**用户电话**；
- 「退款管理」：**待审核 tab 带数量角标**、通过/驳回（理由必填）、凭证图片可点开大图、状态含「超时自动驳回」标记。

### T8 留言管理

1. 「留言管理」→ 应看到已有留言（商品=阿婆牌爱心盖饭、已购 tag、关联订单号）；
2. 点「回复」→ 填写回复内容 → 发布 → 列表「商家回复」列更新（再次回复可覆盖）；
3. 点「隐藏」→ 状态变「已隐藏」→ **去小程序商品留言页确认该条消失**；点「恢复」→ 重新出现；
4. 筛选：商品名称填「盖饭」、是否已购选「已购（关联订单）」→ 可筛出目标记录。

## 四、小程序端测试（微信开发者工具）

> 提示：每次改动管理端数据后，小程序端下拉刷新或重新进入页面即可看到最新值（店铺/菜单走 Redis 缓存，管理端写操作会删缓存）。

### 4.1 首页与浏览（T3/T9）

1. **店铺信息条**：显示店名、「营业中」绿标、公告、营业时间、电话；点电话图标 → 弹出拨号（模拟器可能提示不支持，真机可拨）；**点击店铺条整卡** → 进入「商家信息」页；
2. **商家信息页**：显示状态大标、营业时间、配送说明「配送费 ¥8.00 · 起送价 ¥30.00」（若你在 T2-1 改过）、文字地址、**地图组件显示店铺位置 marker**；
3. **堂食/外卖切换**：点「🍜 堂食」→ 右侧显示「桌号：点击选择」；点它输入 `8` → 显示「8 号」；点「🛵 外卖配送」→ 右侧显示起送价/配送费；
4. **菜单列表**：左侧分类（阿婆招牌/清爽小食）+ 右侧商品卡（图片、名称、价格 ¥18.00、描述）→ 滚动右侧看左侧高亮是否联动；点左侧分类 → 右侧跳到对应分组；
5. **搜索**：输入「盖饭」回车 → 出现结果卡；点「✕」清空 → 回到菜单；
6. **售罄置灰**（先在管理端把爱心盖饭标记售罄）：首页该菜品**置灰且无「＋」**，但**点卡片仍能进详情**；测完记得在管理端取消售罄。

### 4.2 商品详情与加购（T4）

1. 从首页点「阿婆牌爱心盖饭」（或点「＋」，因它有规格会自动弹窗）→ 详情页：大图、名称、价格、描述、**留言区预览（含已购留言与均分）**；
2. 点「选择规格口味」→ 弹窗：选「大份」（价格变 ¥21.00）、选「辣度-微辣」、「加料-煎蛋+午餐肉」（多选）→ 数量点「＋」到 2 → 按钮显示「加入购物车 · ¥42.00」→ 点击 → 提示「已加入购物车」；
3. 返回首页：**左下角购物车栏**出现，数量角标有弹跳动画；点「＋」（无规格菜品时）会有**抛物线飞入**动画（若商品有规格则会跳详情弹窗）；
4. 点购物车栏「去结算」→ **购物车页**：显示明细（规格口味快照）、单价、数量；
5. 在购物车页点「＋/－」改数量（减到 0 会二次确认移除）、试「清空购物车」→ 再重新加购一份。

### 4.3 确认订单与下单（T4/T5）

1. 购物车页点「去结算」→ **确认订单页**；
2. **堂食**：上方切「🍜 堂食」→ 选桌号（如 8）→ 菜品清单、备注填写「少放辣」、预留电话；金额 = 菜品合计（**无配送费**）；点「提交订单」；
3. 下单成功后 → **收银台页**：应付金额、**倒计时（10 分钟）**、订单号、桌号、菜品摘要、支付方式「微信支付（模拟）」带「模拟支付，仅用于演示」说明；
4. 先不支付，做**外卖单**验证配送费与起送价：回首页加购「阿婆牌爱心盖饭 x1」（¥18）→ 购物车 → 去结算 → 切「🛵 外卖配送」→ 选地址（若无地址点「＋ 新增地址」填联系人/11 位手机号/省市区/详址 → 保存）→ 应提示**「还差 ¥12 起送」且提交按钮置灰**（起送价 ¥30）→ 再加购到合计 ≥30（如数量 2，¥36）→ 此时应付 = 36 + 8（配送费）= **¥44** → 提交；
   > 若起送价仍是默认 20，则 ¥18 会提示「还差 ¥2」。
5. 外卖单提交后同样进入收银台。

### 4.4 模拟支付与支付成功页（T5）

1. 在收银台点「确认支付」→ 弹确认框「是否确认支付？模拟支付，仅用于演示，不产生真实扣款」→ 确认；
2. 跳**支付成功页**：✅ 动画 + 彩点、支付金额、订单号、状态、桌号；
3. **幂等验证**：返回该订单再点支付 → 应提示「订单已支付，请勿重复支付」；
4. **销量验证**：
   ```bash
   docker exec takeout-mysql mysql -uroot -proot -N -e "select name,sales from takeout.biz_goods where id=1;"
   ```
   每支付一单，`sales` 应增加该单数量。

### 4.5 订单中心（T6）

1. 首页「🧾 我的订单」→ 订单列表：状态 tab（全部/待支付/进行中/已完成）；卡片含状态徽标、菜品缩略图、件数、金额、下单时间；
2. **取消订单**：找一笔待支付单 → 点「取消订单」→ 确认 → 状态变「已取消」；再点一次（若按钮还在）或重复调用应提示「订单已取消，请勿重复操作」；
3. 点订单卡片 → **订单详情**：状态大字 + 进度条、桌号/地址快照、明细、金额汇总、备注；
4. **配送中退款限制**（堂食看不出，见 4.7 外卖流程）：外卖单处于「配送中」时，详情页底部应显示**灰色「配送中请联系商家协商」**且无申请退款入口。

### 4.6 订单流转（管理端 + 小程序联动）

1. 管理端「订单管理」→ 找到你刚支付的那笔单（状态「待接单」）→ 点「接单」→ 状态变「已接单制作中」；
2. 小程序订单详情 → 下拉刷新/重新进入 → 状态同步为「制作中」，进度条第 3 步高亮；
3. 管理端依次点「出餐」→（堂食单）「确认完成」；（外卖单）「开始配送」→「确认送达」；
4. 观察小程序端状态同步（待取餐/配送中/已完成）；
5. **幂等验证**：在管理端对同一单重复点「接单」→ 应提示「操作失败：订单当前为【已完成】，无法接单」之类精确提示。

### 4.7 退款流程（T7）

**正常通过流程**：
1. 重新下一单并支付（保持「待接单」或「制作中」状态，**不要**在管理端流转到已完成）；
2. 小程序 → 我的订单 → 该单详情 → 「申请退款（¥xx）」→ **退款申请页**：整单退款金额、可点「☎️ 联系商家」、填写退款原因（如「点错了」）、上传 1–2 张凭证图片 → 提交 → 返回详情页出现**「退款进度」卡（审核中）**；
3. 此时在管理端对该单点「接单」→ 应被拒（**「订单退款审核中，流转已暂停」**，验证主状态冻结）；
4. 管理端「退款管理」→ 待审核角标 +1 → 点「通过」→ 确认 → 状态「已通过」；
5. 小程序详情页 → 显示**「已退款」**（终态），底部无操作按钮；管理端再点流转 → 应提示「订单已退款（终态），禁止流转」。

**驳回后可再次申请**：
6. 另下一单并按上面步骤 1–2 申请退款；
7. 管理端「退款管理」→「驳回」→ 填写驳回理由（如「已开始制作」）→ 确认；
8. 小程序详情页 → 显示商家回复（驳回理由），**「申请退款」按钮恢复可点** → 再次申请会新增一条记录，历史保留（详情页退款进度卡可见两条）。

**超时自动驳回（可选，需手工造数）**：
```bash
# 把某待审核退款单的申请时间改到 25 小时前
docker exec takeout-mysql mysql -uroot -proot -e "update takeout.biz_order_refund set create_time=date_sub(now(), interval 25 hour) where id=<退款单ID>;"
```
然后在管理端「系统监控 → 定时任务」找到「阿婆干饭社-退款超时自动驳回」→ 点「执行一次」→ 该退款单变为「**超时自动驳回**」（is_auto_reject=1），订单恢复可流转。

### 4.8 商品留言（T8：仅买过可留言）

1. 商品详情页 → 点留言区「全部 ›」→ **商品留言页**：平均分、条数、「仅购买过的用户可留言」提示、留言列表（含「已购」角标与商家回复）；
2. **未购拦截**：用**没买过该商品的账号**（如 H5 调试用户，或新清缓存后重登）→ 点「✍️ 写留言」→ 应提示**「购买该商品后才能留言哦～」**；
3. **已购发表**：用买过的账号 → 写留言 → 弹窗：**选择关联订单**（chip）、点星 5 星、输入内容、上传图片 → 发布 → 列表出现新留言（带「已购」角标）；
4. **敏感词拦截**：内容里包含词库中的敏感词（词库见 `ruoyi-user-api/src/main/resources/sensitive/sensitive-words.txt`，如「刷单」「博彩」「加微信」）→ 发布 → 应提示**「留言内容包含敏感词，请修改后发布」**；
5. 管理端「留言管理」对该条回复/隐藏，回小程序验证（见 T8 节）。

### 4.9 商家信息与打烊（T9/T5）

1. 管理端「店铺信息」把**营业状态切为「已打烊」**→ 保存；
2. 小程序：首页店铺条变「已打烊」灰标；**仍可浏览菜单**；尝试下单 → 应提示**「店铺已打烊，暂时不能下单」**；确认订单页会显示打烊提示；
3. 商家信息页顶部出现「已打烊，暂时无法接单」提示条；
4. 恢复「营业中」。

### 4.10 超时关单（T5/T6，可选）

1. 下一单**不支付**，记下订单号；

## 七点五、二期 AI 智能问答测试（RAG）

> 前置：环境与后端已启动（redis 必须是 **redis-stack** 镜像，含 RediSearch 模块——已在 compose 中配置）。
> 本文档默认已上传示例知识库；如需从零验证，见下方步骤 1。

### 1. 管理端：知识库上传与解析

1. 登录管理端（http://localhost，admin/admin123）→ 左侧「AI 知识库」（**若看不到请重新登录**，菜单是新增的）；

4. 点「重新解析」→ 状态重新走一遍（验证先删旧向量再入库）；
5. **验证向量确实入库**（应输出 2 左右的数字 + 索引名）：
   ```bash
   docker exec takeout-redis redis-cli --scan --pattern "takeout:ai:vector:*" | wc -l

   ```
   期望：向量条数 >0；索引名 `takeout-ai-index`；`dim` 为 **1024**（通义 embedding 维度）。

### 2. 小程序：AI 助手问答（核心验收）

   - 结合了知识库内容（提到"少油少盐""本地当季新米""慢火焖煮"等**文档里才有的细节**）；

   - 结尾有**"以上建议仅供参考，具体请遵医嘱"**类提醒；
4. **流式输出观察**：回答应**逐字出现**（打字机效果，末尾有闪烁光标 ▍），而不是等十几秒后整段弹出——这是流式输出生效的标志；

## 七点六、中文乱码排查（重要）

**本项目编码链路本身正常**（浏览器/小程序写入的中文读写一致，已实测验证）。如果看到中文乱码，按下面顺序排查。

### 1. 先跑自检脚本（一键定位）

```bash
cd C:\software\code\takeout\ruoyi-takeout-shop
bash scripts/check-encoding.sh
```

- 全部显示 `OK` → 编码链路正常，无乱码；
- 显示 `乱码 xxx —— 发现 N 行` → 会列出具体的表、字段、id 与预览值。

### 2. 按结果分情况处理

| 情况 | 判断 | 处理 |
|---|---|---|
| 乱码集中在**测试数据**（id 偏大、时间集中在某次测试） | 测试时用 Git Bash 的 `curl -d "中文"` 发送，中文被转成 GBK 字节写入 | 清理这些测试数据即可（可参考开发任务记录中的清理思路） |
| **页面新写入的中文也乱码** | 可能是数据库/表字符集问题 | 检查：`docker exec takeout-mysql mysql -uroot -proot -e "show create table takeout.业务表名;"`，字符集应为 `utf8mb4` |

### 3. 正确的测试姿势（防复发）

- ✅ 用**页面操作**（管理端浏览器 / 小程序）——最贴近真实场景；
- ✅ 用 `node` / Postman / Apifox 发请求；
- ✅ 非要用 curl 传中文时，**把请求体写入文件**再发送：

```bash
cat > /tmp/body.json <<'EOF'
{"reason":"菜品凉了，吃不下"}
EOF
curl -X POST http://localhost:4121/api/refund/apply \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  --data-binary @/tmp/body.json
```

- ❌ **不要** `curl -d "中文内容"` —— Git Bash 会把中文转成 GBK 字节，服务端按 UTF-8 解码后变成乱码并永久入库。

### 4. 补充说明

- MySQL **初始化脚本**中的中文乱码是另一类问题（容器内客户端默认 latin1），已在初始化 SQL 文件头用 `SET NAMES utf8mb4;` 修复，与本节无关；
- 若手工往容器里导中文 SQL，务必加字符集参数：

```bash
docker exec -i takeout-mysql mysql -uroot -proot --default-character-set=utf8mb4 takeout < 你的文件.sql
```

## 七点七、小程序编译报错排查（导入/导出）

**典型报错**：
```
"BASE_URL" is not exported by "utils/request.js", imported by "utils/upload.js"
```

**原因**：`utils/*.js` 中的变量/函数漏写 `export`，而页面里用的是**具名导入** `import { X } from '@/utils/request'`，因此解析不到。

**一键自检**（推荐每次改动 utils 或新增页面后先跑）：

```bash
cd C:\software\code\takeout\takeout-uniapp
node scripts/check-imports.mjs
```

- 输出 `所有导入均可解析 ✅` → 正常；
- 输出 `❌ 文件 → 从 xxx 导入 [名字] —— 该文件未 export 这些名字` → 按提示在对应 utils 文件补 `export`（或把引用处改为默认导入 `import request from '@/utils/request'`）。

**两种导入写法（本项目都支持，任选其一但要对应）**：

```js
// 写法 A：具名导入（utils 里必须有 export 关键字）
import { request, ensureLogin, BASE_URL } from '@/utils/request'

// 写法 B：默认导入（使用 request.js 末尾 export default 对象里的键）
import requestUtil from '@/utils/request'
requestUtil.request({ ... })
```

> 提示：本项目 `utils/request.js` 同时提供了**具名导出**与**默认导出**，两者名字一致（`request / login / ensureLogin / getToken / getMember / clearLogin / BASE_URL`），`upload.js` 另导出 `uploadImage / chooseAndUploadImages`，`dining.js` 导出 `getDining / setDining / setTableNo / parseSceneTableNo`。

**其他常见编译报错**：

| 报错 | 原因 | 处理 |
|---|---|---|
| `Cannot find module '@/utils/xxx'` | 文件不存在或路径拼错 | 检查 `utils/` 下文件名与实际引用是否一致 |
| `Browserslist: browsers data is X months old` | 只是提示，非错误 | 可忽略；想消除执行 `npx update-browserslist-db@latest` |
| 页面白屏但无报错 | 该页未在 `pages.json` 注册 | 检查 `pages.json` 的 `pages` 数组是否包含该页面路径 |
